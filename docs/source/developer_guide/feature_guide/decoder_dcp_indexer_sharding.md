# Request-sharded Lightning Indexer cache on the DCP decoder

**Design proposal for `feat/decoder-dcp-indexer-sharding`.** Give each decoder request one Group-1 owner in its local DCP group. That rank holds every position of the request's indexer keys and scales and computes its Lightning Indexer rows. All DCP ranks receive the ordered global token IDs. Each rank then retrieves and attends to its own Group-0 latent/RoPE stripes. Ownership lasts for one allocation generation, irrespective of the request's batch row.

## Running the experiment

Set `VLLM_ASCEND_DSA_DCP_INDEXER_REQUEST_SHARDING=1` in the **decoder** launch environment and restart the decoder workers. The default is `0`. Use the matching feature checkout in all four repositories. The production receiver uses process storage, asynchronous loading, a persistent direct-HBM Group-1 reader and a shared two-group pool. Startup checks compare the KV spec across TP ranks before allocating the slabs. Existing Mooncake pages can be restored by a new owner.

The following command runs the replicated and owner-sharded C8 paths on the same four test NPUs. Both arms include current cache writes, the resident planner, registered-host H2D, native sparse attention and DCP output exchange across four layers. The result includes replay parity, slowest-rank timing and indexer key/scale storage bytes. Those bytes describe the benchmark tensors. The server retains its configured HBM slab budget.

```bash
cd /workspace/sqh/vllm-ascend
HCCL_OP_EXPANSION_MODE=AIV TASK_QUEUE_ENABLE=1 python3 -m torch.distributed.run \
  --nnodes=1 --nproc-per-node=4 --master-addr=127.0.0.1 --master-port=29571 \
  benchmarks/ops/benchmark_sfa_dcp_indexer_sharding.py \
  --lmcache-ascend-dir /workspace/qzy/LMCache-Ascend --requests 1 2 4 8 \
  --history 16384 --layers 4 --steps 4 --trials 3 --iterations 3 \
  --json dcp-indexer-balanced.json
```

Use `--owner-layout skewed --skew-history` to exercise a nonzero owner and empty peers. Use `--replicate-owner-storage` to measure owner computation with replicated history. Both modes use the same shared-index consumer chain.

## Deployment and memory contract

The supplied GLM-5.3 launcher uses TP4/DCP4 per decoder instance, DP/EP across instances, 128-token blocks and interleave, one MTP draft token, up to 16 requests and 256 scheduled tokens. It enables mixed-capable C8 indexing, full SFA graphs, async MTP preparation, shared plans, retrieval overlap and early query gathering. Its request capture sizes are 2, 4, 8, 12, 14 and 16. The playbook allows 1,048,576 tokens. P uses four-bank prefill and both roles use `kv_both`.

Propose a single default-off flag, `VLLM_ASCEND_DSA_DCP_INDEXER_REQUEST_SHARDING=1`, in the launcher's `node_kind=D` block. Resolve it once through Ascend's existing decoder DCP validation and LMCache receiver policy. Propagate the resolved mode through the KV specs/config to the scheduler, target and draft workers, and connector. Keep the positional sharding factors at `[D, 1]` for Group 0 and Group 1. Setting Group 1's `dsa_dcp_size` to `D` would stripe each request's history and break the full-history owner contract. Keep the launcher's `enable_dsa_cp=false` and FlashComm1 settings. Compare layout versions within the local DCP group at startup. The prefiller, DCP1 and default mode follow their existing paths. For the first release qualify the supplied process-backed, async, persistent-direct-HBM decoder. A receiver requesting an unsupported combination must get a startup error before HBM is allocated. [Decoder qualification](https://github.com/shaaaaaa/vllm-ascend/blob/b7b03d40cbaf5d29012aac7c1ff19becee4a39a2/vllm_ascend/worker/worker.py#L480) · [Ascend cache spec](https://github.com/shaaaaaa/vllm-ascend/blob/b7b03d40cbaf5d29012aac7c1ff19becee4a39a2/vllm_ascend/patch/platform/patch_kv_cache_interface.py#L19)

For request `i` let `P_i = ceil(allocated indexer positions / 128)`, including reserved lookahead. Replication requires `D × sum(P_i)` live Group-1 page copies. Request ownership requires `sum(P_i)`, with `sum(P_i for owner r)` on rank `r`. Apply the same accounting to each physical indexer layer's keys and its C8 FP16 scales. Shared-index consumer layers acquire no additional key cache.

| DCP4, 16,384 positions per request, before lookahead | Replicated | Request-sharded |
|---|---:|---:|
| 16 requests, group-wide live indexer pages per physical indexer layer | 8,192 | 2,048 |
| 16 requests, busiest rank under balanced placement | 2,048 | 512 |
| One request, busiest rank | 128 | 128 |

The factor of four is an aggregate live-cache guarantee. One long request must fit on one owner. With the launcher's maximum context that can be 8,192 Group-1 pages before bundle and other cache charges. Workers preallocate their HBM slabs under the 0.93 utilization budget. At a fixed budget the saving buys admission headroom. To return reserved HBM at fixed service capacity, size fewer physical parents per worker against the busiest owner, the required Group-0 parents and the single-request floor. Use the actual layout byte calculation, explicit block budget and graph-memory profile. Report live key/scale bytes, occupied physical parents, reserved slab bytes and graph workspace separately. Existing null storage, alignment, partial final pages, scale sidecars and latent-only layer slabs still cost bytes. The existing sizing code explicitly charges those latent-only layers. For a fixed workload, measure the high-water occupied and quarantined parents per rank, size to the maximum over ranks, and verify the same admissions with the existing `--num-gpu-blocks-override`. Independently shrinking latent-only backing would need a separate capacity for those tensors and a layer-class-specific Group-0 physical map in both attention and transfer. ## Physical placement and admission

Today one scheduler parent allocator serves both logical groups. A request receiving a fraction of a bundle is handed every sibling block in it. A common-parent design that lends out individual rank copies of Group 1 still strands space. With two parent numbers on each of two ranks, put Group 1 in parent 1 on rank 0 and parent 2 on rank 1. Both ranks can supply a Group-0 parent. Requiring the same number on both ranks rejects the allocation. [Shared coordinator](https://github.com/shaaaaaa/vllm/blob/5bf81c88f035ad72254a63b4b78c41b567dc07ac/vllm/v1/core/kv_cache_coordinator.py#L132) · [Current block allocation and reference counts](https://github.com/shaaaaaa/vllm/blob/5bf81c88f035ad72254a63b4b78c41b567dc07ac/vllm/v1/core/block_pool.py#L107)

Use one scheduler-owned physical parent allocator **per DCP rank**, all backed by the existing per-rank geometry. The scheduler already owns admission and can maintain these free counts locally.

- A logical Group-0 bundle reserves one physical parent on every rank in a single transaction. Store the vector of physical parent numbers. The example above allocates `(2, 1)`. Keep the existing per-request Group-0 bundle rounding, stripe formula, compact scratch origin and release-frontier rules. Translate the bundle number before deriving the rank's physical Group-0 block table. The resident planner, H2D copier and SFA then see ordinary local physical addresses.
- A Group-1 allocation reserves canonical 128-position pages on the owner alone. Track free page positions inside each owner-local Group-1 parent. Reuse suitable free positions across requests, favor tightly packed parents and contiguous runs where available, and open another parent only for the remainder. Index free positions using the existing bitmap approach as a pattern. One page is exclusive to a request generation. Siblings can belong to different requests. With 18 indexer pages per mixed paired parent, four 128-page requests on one rank can share 29 parents when tightly packed. Rounding each request separately would reserve 32. Reserve whole parents against Group 0 while any Group-1 page is live or held for DMA. Return the parent when its last page is reusable. Other ranks may simultaneously use that physical number for either group.
- Derive canonical local page IDs using `layout.block_ids_for_bundle`. The mixed paired layout has nonconsecutive NoPE/RoPE bank ranges. Its C8 layer mapping and FP16 scale plane have to describe the same logical token. For attention, translate the owner-local canonical ID through `MixedIndexerMetadata` where applicable. For LMCache, pass canonical owner slots to its existing per-plane address planner, which already applies the C8 mapping and splits noncontiguous runs. Applying the map twice changes the address. [Bundle geometry](https://github.com/shaaaaaa/vllm/blob/5bf81c88f035ad72254a63b4b78c41b567dc07ac/vllm/v1/core/dsa_shared_pool.py#L262) · [Mixed C8 metadata](https://github.com/shaaaaaa/vllm-ascend/blob/b7b03d40cbaf5d29012aac7c1ff19becee4a39a2/vllm_ascend/worker/dsa_shared_pool.py#L28) · [Direct page destinations](https://github.com/qiuziyan1998/LMCache-Ascend/blob/a357f7b1c82e20052e27e08380439f0b857e3be9/lmcache_ascend/v1/npu_connector/npu_connectors.py#L5163)

For a particular allocation let `g` be the additional physical Group-0 parents required **per rank**, `i` the new Group-1 pages required by this request, `F[r]` the entirely free parents on rank `r`, `h[r]` the allocatable pages inside its already-open Group-1 parents and `b` the layout's indexer pages per parent. With candidate owner `o` the capacity test is

```text
F[r] >= g                                      for every r other than o
F[o] >= g + ceil(max(0, i - h[o]) / b)
```

Calculate incremental demand after existing allocations, external-hit extent, future accepted positions and MTP lookahead are accounted for. A partial Group-1 parent can satisfy Group-1 growth and cannot satisfy a whole Group-0 allocation until released. This is measurable within-rank fragmentation. This accounting removes phantom nonowner reservations and the common-parent-number constraint while keeping the existing whole-bundle unit for Group 0.

Among feasible owners, minimize the projected maximum of `sum(visible history length × scheduled indexer query rows)` for the active requests on each rank. A deterministic tie-break prefers fewer new parents, then the lower local rank. Charge memory as soon as the async load is admitted. Maintain the load estimate on the host at admission, growth, resume and completion. On owner-local pressure, prioritize a policy-eligible victim whose release helps the constrained rank. For common Group-0 pressure, consider all binding ranks. Defer if the policy permits no helpful victim. Ordinary batch reordering never migrates live history.

Implement planning and rollback around both `allocate_new_computed_blocks` and `allocate_new_blocks` inside `KVCacheManager.allocate_slots`. Reserve the complete delta, commit once, then let `update_state_after_alloc` expose destinations. Journal parent allocations, subpages, logical handles and request-table tails so any partial failure restores the prior state. Repeated pending lookups cannot allocate a second owner. Default, dynamic and Ascend recompute schedulers share this entry point. Update the startup maximum-length checks and concurrency estimates to use the new capacity model. [Allocation sequence](https://github.com/shaaaaaa/vllm/blob/5bf81c88f035ad72254a63b4b78c41b567dc07ac/vllm/v1/core/kv_cache_manager.py#L420) · [Recompute admission and async handoff](https://github.com/shaaaaaa/vllm-ascend/blob/b7b03d40cbaf5d29012aac7c1ff19becee4a39a2/vllm_ascend/core/recompute_scheduler.py#L674)

## Placement metadata and worker tables

Use a versioned, value-only placement record scoped to `(request_id, allocation_epoch)`. It contains the owner rank, the logical Group-0 bundle to rank-local parent assignments, and the Group-1 logical page to owner-local canonical page assignments. Logical handle namespaces distinguish groups and live allocations, reserve zero for padding, and permit reuse only under the lifetime rules. Put the mapping behind the new decoder allocator. Existing pool callers use the legacy representation in the default mode.

Pass the placement into the group managers as part of the request's reservation. A mutable global “current owner” would let a cold load or another request inherit the wrong placement. Send a full record on first admission or replacement after resume and append deltas on growth. A shared Group-0 parent number can be encoded once when all ranks received the same number. Carry a vector only when they differ. Make it available in `NewRequestData` / `CachedRequestData` **and** connector-only `ReqMeta`. A request can enter `WAITING_FOR_REMOTE_KVS` before there is a model forward. Keep immutable snapshots for saves and preemption. Decode handles at the worker boundary before block-table append/replace, slot calculation, cache zeroing, direct DMA or diagnostics that inspect an address. Zero only the newly allocated group, page and owning rank. Bulk zeroing sibling pages could erase another request. For Group 0, build a rank-local view for `DsaDcpDenseLoad.select` and `DcpWriteLayout.runs`, including compact `live_origin`. Control agreement uses the shared placement identity while each worker executes its own physical map. ## Restore, publication, checkpoint and failure

| Operation | Data movement and completion |
|---|---|
| P-to-D cold restore | P publishes the existing canonical Mooncake pages. In `persistent_direct_hbm` mode the RemoteFill direct groups are already `(0,)`. D keeps the Group-0 import on its current participants. Keep reader preflight on all possible owners. Only the current owner builds a token-level Group-1 slot mapping and calls `load_group1_pages_direct` into its final HBM. For checkpoint restore the owner reads the aligned persistent prefix and the leased checkpoint tail through their respective existing paths. Validate its full hit extent and key/scale planes. Keep the existing single outstanding direct-load admission limit for this trial. |
| Readiness | Carry owner and allocation epoch beside the existing load attempt/generation. Distinguish “these keys are local” from “the owner is ready for this generation.” Nonowners complete their Group-0 work and release imported leases. Only completion after the owner's DMA can certify its Group 1. The existing source-import vote precedes `indexer.result()`. Use the existing generation-matched completion aggregation, or an ordered final load vote if needed, after that result. Every participant still enters the existing checkpoint-prefix vote in the same order. Update graph readiness and eager checks currently reading `indexer_npu_resident`. |
| Ordinary or windowed save | Honor the existing `can_save_latent` and `can_save_indexer` gates. Capture every required Group-0 stripe into its canonical offsets. The owner validates the Group-1 source and writes its key/scale interval exactly once into the existing storage reservation. Rank 0 keeps reservation, token hash/key construction and commit/publication authority. Give a nonzero owner access to the reservation through the existing participant descriptor. Nonwriters still acknowledge and release holds. |
| Checkpoint and resume | Snapshot owner, allocation epoch, rank-local Group-0 tables, owner Group-1 pages and the original promised frontier before scheduler release. Capture precedes next-step writes on the worker. All ranks retain Group-0 stripe duties. The owner captures the Group-1 prefix/tail required by existing checkpoint rules. Keep TP0 seal/cancel, accepted-token reconciliation, bounded CPU reclaim, participant ACKs and quarantine on unknown DMA completion. Resume can pick another owner in a fresh allocation epoch and restore exactly the sealed extent. |
| Errors and reuse | Bare physical block numbers can repeat across ranks, groups and later occupants. Carry `(request_id, allocation_epoch, load_generation, group, failed logical extent)` through connector output aggregation and invalidation for this mode. Match success as well as failure against the current attempt. Retire stale leases without invalidating the new occupant. A failed owner fails that attempt on all ranks. Defer physical reuse until ordered capture/drain makes the old reads and writes safe. An unknown completion uses the existing fail-stop/quarantine policy. |

1. **Benchmark the producer chain on A2.** A test-only variant keeps replicated storage and compares replicated compute against compact owner compute with the real C8 scorer, packed projections, ID exchange and inverse.
